= Tool approval
:toc:
:toc-title: Contents

This document describes how user confirmation (Accept / Reject) works before the executor runs a tool.

== Wiring (when a conversation is opened)

DefaultToolExecutor was introduced. It is a class, which executes tool requests using virtual threads (one per tool execution).
It has a before tool execution gate, which is executed before every tool call.

There is WaitForApprovalGate, which waits for user approval.

`ChatSessionFactory`, currently always installs `WaitForApprovalGate` as the default in `MultipleToolExecutionGate`.
The UI attaches later, in `ChatViewModel.attachToSession()`.

== How approval works

The important detail: *two threads*.

[cols="1,2"]
|===
|Thread |What it does

|Streaming / executor
|`executeTools` → gate → `future.get()` — *waits*

|JavaFX
|Adds the bubble, shows the buttons, completes the `Future` after a click
|===

When tool call request comes from LLM, then it is sent to the view, view adds a `tool call message`, to messages list, which is bind with a view ToolCallChatMessageViewModel. Later
`StreamingChat.executeTools()` at some point call askForApprovalGate, and this calls approval provider:

. first `onMessageAdded(TOOL_CALL)` — queues adding the bubble on the FX thread
. then approve gate waits for on approval
. the approval result is passed to a gate, and gate proceeds

The approval provider *finds* the `ToolCallChatMessageViewModel` by the tool request id.
If that bubble is missing, it completes the future with `ERROR`.
It does not create a view model.

The FX thread usually adds the bubble before that lookup.
`onMessageAdded(TOOL_CALL)` is queued first; `askForApproval` looks the bubble up afterward, also on the FX thread.

== Stop

Stop abandons this turn. It does not Accept or Reject the tool.

. `ChatViewModel.stopMessage()` publishes `StopRequestEvent` only.
. `StreamingChat` sets `stopRequested` and, when the executor is `ICancellable`, calls `IToolExecutor.cancel()`.
. `DefaultToolsExecutor.cancel()` forwards to the gate. `MultipleToolExecutionGate` passes that on to `WaitForApprovalGate`, which completes each pending future with `CANCELLED` (`"Chat stopped by user"`).
. `REJECTED`, `ERROR`, and `CANCELLED` all mean the tool does not run. The executor still returns an error tool-result.
. Accept / Reject buttons hide because `requestApproval` registers `whenComplete`, which clears `needsApproval` when the future finishes — including when the gate completes it as `CANCELLED`.
. After `executeTools()`, if `stopRequested` is set, `StreamingChat` calls `onCancel()` and does *not* start another `chatModel.chat()`.

A tool that already passed the gate keeps running until `executeTools()` returns.

== Switching conversation

`loadConversation` still refuses to switch while `sendingMessageInProgress` is true.
Stop clears that flag in `onCancel`, so after Stop the user can switch conversations and send again.

== Decision path (short)

[plantuml]
----
@startuml
start
:LLM wants a tool;
:TOOL_CALL bubble in chat;
if (Find bubble by tool request id?) then (missing)
  :ERROR, tool does not run;
  :TOOL_RESULT in chat;
  :Next LLM turn;
else (found)
  if (Accept?) then (yes)
    :Tool runs;
    :TOOL_RESULT in chat;
    :Next LLM turn;
  else (no)
    if (Reject?) then (yes)
      :REJECTED, tool does not run;
      :TOOL_RESULT in chat;
      :Next LLM turn;
    else (Stop)
      :CANCELLED, tool does not run;
      :Error tool-result recorded;
      :onCancel, no next LLM turn;
    endif
  endif
endif
stop
@enduml
----

Stop ends the turn.
Accept and Reject are the decisions that continue into a follow-up LLM call.
A missing bubble is `ERROR`: the tool does not run, the error result is still sent back, and the next turn still runs.
